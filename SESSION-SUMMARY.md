# VRK Partners — сводка проделанной работы (сессия Cowork, июль 2026)

## 1. Контекст проекта

**VRK Partners** — лидген-лендинг (uk-UA, одна страница + /thanks) + админка-CRM на Next.js 15 (App Router, TypeScript strict), Supabase (Auth + Postgres + RLS), Tailwind (лендинг — бренд-тема, админка — shadcn/ui), Vercel (деплой из `master`, GitHub `nikolaevmaxim05-ctrl/VRKPartners`). Конвейер заявки: rate limit (Upstash) → honeypot → Zod → Turnstile → дедуп → Supabase + Telegram + KeyCRM + Email (Promise.allSettled). Воронка стадий порождает офлайн-конверсии Google Ads (+ корекції RETRACT/RESTATE, фид в Google Sheets). Проект готовится к передаче клиенту. Отправная точка сессии — файл секьюрити-ревью `review20260713.md` (29 находок: G1–G2, S1–S9, C1–C18).

## 2. Формат работы

Основной режим: **я (Cowork) пишу промт-файлы для Claude Code**, кладу их в корень проекта (`PROMPT-*.md`), пользователь запускает:

```
claude "Выполни задачу из PROMPT-<имя>.md"
```

Каждый промт — самодостаточный (Claude Code не нужен внешний контекст), на русском (тексты UI внутри — uk-UA). Помимо промтов делались и прямые аналитические задачи (разбор логов, аудит зависимостей).

## 4. Шаблон промта (выработанный в сессии)

Каждый PROMPT-*.md строится одинаково:

1. **Заголовок-задача + контекст проекта** (одна строка: стек, uk-UA, что уже есть).
2. **Диагноз/предыстория**, если задача — фикс (что сломано, гипотеза причины, как проверить).
3. **Что нужно** — нумерованные требования, максимально конкретные (пути файлов, значения, цвета, тексты кнопок дословно).
4. **Как реализовать** — архитектурные решения приняты заранее (какой компонент, где хранить, какой механизм), чтобы Claude Code не изобретал своё.
5. **Чего НЕ делать** — явные запреты (не рефакторить попутно, без новых зависимостей, не трогать submit-логику, не копировать чужие тексты, не выдумывать реквизиты/данные).
6. **Проверка** — build+lint+test зелёные, ручной smoke-чек-лист по пунктам, требования к тестам.
7. **Отчёт** — что перечислить в конце (изменённые файлы, места применения, отклонения от ТЗ с обоснованием).

## 5. Постоянные правила (инварианты, повторяются из промта в промт)

- **Язык:** весь видимый UI — только uk-UA; общение и промты — на русском.
- **Не ломать сильные места** из ревью: конвейер /api/lead (Promise.allSettled — лид не теряется), AES-GCM шифрование интеграций, whitelist'ы, иерархию ролей, CSP/HSTS, noindex /thanks и /admin, лёгкий лендинг (тяжёлое — только в admin-чанках).
- **Реестр аналитики — контракт:** новое событие = сначала регистрация в analytics-registry, иначе контракт-тест падает; схема имён GA4-style (`telegram_click`, `generate_lead`…), `form_start`/`form_submit` запрещены.
- **Конфиг-паттерн «без деплоя»:** всё клиентское — дефолты в коде (`config/site.ts`) + оверрайды в БД, редактируемые из админки; fail-safe (ошибка БД → дефолты); `revalidatePath` после мутаций.
- **БД:** существующие миграции не редактировать — только новые, по порядку.
- **Git:** отдельный коммит на логическую единицу, префикс номера находки/фичи.
- **Без новых зависимостей** без необходимости; иконки — инлайн-SVG.
- **Безопасность по умолчанию:** проверка прав на каждом admin-роуте, Zod на входе, plain-text от админа (никакого raw HTML), валидация URL (только https/t.me).
- **Запрещено:** сервисы рос. юрисдикции (Яндекс, VK, Mail.ru), токены в коде, PII в localStorage.

## 6. Типовые результаты и извлечённые уроки

- **Итеративность фич:** контакты прошли 2 итерации (копирование+ссылка → только копирование, tel: на мобильных — Outlook на ПК оказался проблемой), Telegram-кнопка — 2 итерации (добавить → переставить и переоформить), юрстраницы — 3 (заглушки → готовые тексты + админ-редактор → UI редактора). Вывод: закладывать редактируемость и переиспользуемые компоненты сразу — все итерации ложились в уже созданную структуру.
- **Инцидент деплоя:** commit eb97bb4 ушёл без файла из рабочей копии → Vercel упал, локально всё собиралось. Урок закреплён в промтах: финальная проверка включает `git status` чистый, warning'и импортов в билде = блокер.
- **Кросс-задачные хвосты:** правка C12 (батч интеграций) сломала моки тестов трёх интеграций — фиксы безопасности и фичи гоняются одним и тем же циклом проверки (build+lint+vitest, ~293 теста).
- **Передача клиенту** — сквозная тема: ничего клиентского не хардкодить, внутренние файлы (PROMPT-*, DEPLOY-TODO, SETUP-PLAN) перед передачей удалить из репо (G2), доступы по HANDOVER-checklist, юртексты показать юристу, реквизиты клиент добавит сам через админку.
